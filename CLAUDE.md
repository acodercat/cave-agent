# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

CaveAgent is a Python agent framework that enables LLM function-calling through code generation (not JSON schemas) with persistent Python runtime state. It natively handles complex objects like DataFrames and ndarrays within a stateful runtime across multi-turn interactions.

## Architecture

### Agent Execution Loop (`agent.py`)

`CaveAgent` streams a model response, stops at the first complete code block, executes it, appends the result as an `ExecutionResultMessage`, and repeats until the model answers without code or a limit is hit.

**There is exactly one execution path.** `run()` drains `stream_events()` and builds an `AgentResponse` from the terminal `StoppedEvent`, so a run behaves identically whether or not the caller consumes events. Do not add a second non-streaming loop — the previous design had one, and the two silently diverged (streaming executed one code block, non-streaming concatenated and executed every block in the response).

**One code block per turn, parsed exactly once.** The stream breaks as soon as `StreamingTextParser` reports a complete block, then `aclose()`s the provider stream in a `finally` (the SDK's read-to-completion auto-close never fires when you stop reading early). The same `process_chunk` call that reports completion also emits the CODE segment, so `_stream_once` captures it on `_ModelTurn.code` — there is no second parse of the accumulated text. `utils.extract_first_code_block` was that second path and is **gone**: re-parsing text cannot distinguish a closed fence from an unterminated one, so a response cut off mid-block was executed as if the model had finished writing it. A closing fence is recognized only at the start of a line (with up to three leading spaces); ` ``` ` inside a Python string or comment is code, not a fence.

**Fences are line-anchored and the language tag is case-insensitive.** An *opening* fence is only a fence at the start of a line (three-space tolerance, as for closing): recognized mid-line, prose that merely mentioned ` ```python ` — "wrap code in ```python fences like this:" — opened a bogus block that the real block's line-start fence then closed, so the agent executed the prose between them and the actual code was discarded in the remainder. Inline code spans and backtick runs mid-line are prose. The tag matches case-insensitively because Markdown's info string carries no case rule and models write ` ```Python ` often enough that a case-sensitive match silently streamed the whole block as prose. The fence-line indent belongs to the fence, not the code, so the backslash-continuation check strips it first — left in place it hid the trailing backslash, and an indented fence inside a continued string closed the block mid-string.

**An empty fence is not the first code block, and a block is dedented before it runs.** Both follow from that three-space tolerance. Completing on an empty ` ```python``` ` set the flag with no CODE segment, so the agent broke out of the stream with `turn.code is None`: the real block the model wrote next was never parsed and the answer was recorded truncated at the empty one. The opening is replayed as text instead — it is part of what the model wrote — and parsing continues. Separately, because an indented block *closes* correctly, `strip()` alone de-indented only its first line and handed the model `SyntaxError: unexpected indent` for code it wrote right; `_finished_code` applies `textwrap.dedent`, which is a no-op on ordinary source.

**The *first* block, at any chunk size.** `process_chunk` stops on the character that closes the first fence and leaves the rest of that delta in `parser.remainder`; the agent appends only the consumed prefix to `turn.text`. It used to parse the whole delta, so a response carrying two fences in one chunk — routine for a fast model or a buffering proxy — emitted a CODE segment per block and kept the *last*: the agent ran the second block and silently dropped the first. Chunk size is a property of the transport, so any behaviour that varies with it is a defect by construction, and the parser tests are parametrized over 1-char, SSE-sized and whole-response deltas because the 1-char case passes either way. `_reset_state` clears `first_code_block_completed`, since the flag now gates consumption and a flushed parser would otherwise refuse every later chunk.

**A turn knows whether it is whole.** `_ModelTurn.complete` is `error is None and (code is not None or finish_reason != "length")`; incomplete turns carry their text forward in `prefix` and re-stream with `resume_prompt` rather than being recorded as an answer. Both ways a turn can be a fragment — the provider's output cap and natural EOF without a terminal finish reason — set that state before the turn is handled. An early break at the first closed code block leaves `finish_reason` unset and is complete **by design**: the agent chose to stop. A fragment that cannot be recovered stops the run with `MODEL_ERROR`, never `COMPLETED`.

Recovery paths woven into the loop:
- **Output truncation** — `finish_reason == "length"` keeps the partial text and appends `OUTPUT_RECOVERY_PROMPT`, budgeted at `MAX_OUTPUT_RECOVERIES` (3) per run. The prefix seeds the next turn's parser, so a code block split across the boundary still closes and executes as one block.
- **Mid-stream failure** — content already received is kept and `STREAM_INTERRUPTED_PROMPT` asks the model to resume. Distinct from the truncation prompt, which blames the output limit — wrong advice for a dropped connection.
- **Prompt overflow** — `PromptTooLongError` (raised at request time, never mid-stream) triggers `Compactor.recover_from_overflow` and one retry. A second overflow propagates by design.
- **Cancellation / abandoned consumption** — cancellation propagates into `Runtime.execute`, whose backend owns request-scoped cleanup before it re-raises; repeated cancellation cannot interrupt that cleanup, and the agent never sends an untargeted interrupt after the coroutine has unwound, when another caller may already own the shared runtime. `_close_dangling_execution` pairs a trailing `CodeExecutionMessage` with a synthetic result and appends an interruption marker, so a cancelled or explicitly closed stream leaves history reusable by the next `run()`. A drained or cancelled stream emits `StoppedEvent`; `GeneratorExit` cannot legally yield, so early close repairs history without emitting another event.

**Budgets** (`max_total_tokens` / `max_input_tokens` / `max_output_tokens`) are cumulative per run and checked at step boundaries: the crossing step completes and is recorded, the next does not start. Compaction's own LLM calls are excluded from the totals, so leave headroom on compaction-heavy sessions.

**`max_exec_timeout` requires a preemptible runtime** and `__init__` raises `ValueError` otherwise — the unsafe configuration is rejected rather than made available. Execution runs in a task on the caller's loop; `asyncio.wait` detects the deadline without conflating it with a backend-raised `TimeoutError`, then the agent cancels and awaits that task. The backend interrupts the request while it still owns the channel and finishes cleanup before re-raising; an agent-level interrupt could arrive after the channel changed hands and hit unrelated work. If generated code catches `KeyboardInterrupt`, the kernel executor terminates that process before releasing its channel; registered bindings are queued for the lazily started replacement. The timeout event and model-facing result explicitly report the resulting state loss, because arbitrary variables, imports and functions created by earlier model code disappear with the process. Recovery can delay the timeout event briefly, but the expired cell cannot keep running beside the next request. The predecessor offloaded to a worker thread and abandoned it on expiry, which left `IPythonExecutor`'s `capture_output()` — a *process-global* `sys.stdout` patch — unwound out of order, so every later `print` in the host process vanished into a dead buffer.

### Events (`events.py`)

One frozen dataclass per event with named typed fields; consumers `match` on the type. `StoppedEvent` carries `stop_reason`, `steps`, `elapsed` and `usage`. `StopReason` distinguishes `COMPLETED` / `MAX_STEPS` / `TIMEOUT` / `BUDGET_EXHAUSTED` / `CANCELLED` / `MODEL_ERROR` / `RUNTIME_ERROR` / `INTERNAL_ERROR`.

`_initialize_conversation` runs **inside** the envelope: it renders a caller-supplied template and calls the runtime's `describe_*()`, either of which can raise, and outside it that raise escaped with no terminal event at all. A shell/channel timeout surfaces as `RUNTIME_ERROR`, not `MODEL_ERROR` — public execution/allocation paths use the `runtime/base.py` envelope, while the kernel's silent startup path converts its timeout directly because `start()` does not pass through that base class. A dead channel is infrastructure, not a model that needs different code.

The last three are separate on purpose: the provider failed, the runtime failed, or the agent has a defect. Collapsing them sends an operator to read model logs for a dead kernel. `INTERNAL_ERROR` is emitted and the exception then re-raised — reported *and* not swallowed. **A stream consumed to termination ends with a `StoppedEvent`**; `drain_to_response` raises if one never arrives, so the invariant is load-bearing. `stream_events` handles `GeneratorExit` *before* the catch-all arm because yielding in response to an explicit early close raises "async generator ignored GeneratorExit"; that path instead records the interruption between the abandoned request and the next user turn.

`_stream_once` closes the provider stream through `_close_stream`, which is bounded as well as guarded. A closer past its deadline is **cancelled**, not merely abandoned: leaving it running looked gentler, but the cost is one pending task per turn and unbounded. Per-turn close failures are logged and never propagated: closing is cleanup, so it cannot invalidate an answer the provider already declared complete, prevent a closed code block from executing, or replace the read error that ended the stream. The public `Model.aclose()` remains caller-facing and still reports failure. A raise from a `finally` *replaces* what was propagating, and a socket that just died usually fails to close too — unguarded, that ended a cancelled run as `MODEL_ERROR` with the `CancelledError` swallowed, and cost a mid-stream failure the partial content output recovery exists to salvage. Close runs as a task the caller stops waiting on — after `_STREAM_CLOSE_TIMEOUT` (1s) normally, and immediately when the run is already cancelled, where any wait is one the user asked to end. On that path the task is left running for the same grace before being cancelled: cancelling a just-created task runs it zero times, so an earlier version reclaimed the task by guaranteeing the socket was never released. Unbounded, a hanging closer held the loop between reading a complete code block and executing it, and left a cancelled run needing a second cancel.

`ExecutionResultEvent` carries the **full** output plus `success`, and flags `persisted` separately — a renderer shows what actually happened, not the shaped marker the model received.

### Rendering (`renderers.py`)

Fully optional and invisible to the core: there is no display flag on `CaveAgent` and no import of this module from the agent loop (enforced by a test that AST-parses the agent's imports). `TerminalRenderer.render(events)` is pass-through middleware — it renders and re-yields each event unchanged. `render_run(agent, query)` is the convenience form returning an `AgentResponse`.

Markdown rebuilds are time-gated (`_MARKDOWN_REBUILD_INTERVAL`): `TextEvent`s arrive per delta — often per character — and rich's `Markdown` runs a full CommonMark parse of the whole buffer at *construction*, before `Live`'s paint throttle is consulted, so unthrottled rendering was O(n²) CPU on the event loop competing with the provider stream read (~1.4s for a 2.9KB answer). Gated characters are deferred, never dropped — `_stop_live` paints the final state before the block freezes.

This separation is what allows the single execution path above; the old design routed `run()` through streaming purely to feed the UI, and needed function-body imports to dodge an `agent` ↔ `display` import cycle.

### Runtime System (`runtime/`)

`Runtime` (`runtime/protocol.py`) is a `@runtime_checkable` Protocol used for caller-supplied runtimes; `CaveAgent` still imports and constructs `IPythonRuntime` as its convenience default. It includes the `inject_*` registration methods and atomic `inject_resources()` because the agent registers into the runtime itself (skills inject `activate_skill`), not just reads from it. New backends satisfy it structurally; no subclassing required.

`interrupt()` is **not** on `Runtime`. It lives on `PreemptibleRuntime(Runtime, Protocol)`, a capability protocol the agent tests with `isinstance` — presence of the method *is* the claim, so a backend opts in by implementing it rather than by setting a flag. A `preemptible: bool` member would have been *required* of every structural implementer, which is the opposite of what a capability should cost. `BaseRuntime` used to carry an `interrupt()` no-op whose docstring said "best-effort" and whose body was `pass`; that lie is what let a timeout be offered on a runtime that could not honour it.

`BaseRuntime` (`runtime/base.py`) is a convenience base holding the LLM-facing `functions` / `variables` / `types` registries and the `describe_*()` renderers. **It takes its executor as a constructor argument.** The previous arrangement required subclasses to assign `self._executor` before calling `super().__init__()` — an implicit ordering contract that failed with an `AttributeError` several frames from the mistake.

Implementations:
- **IPythonRuntime** (default) — in-process IPython shell. Direct object access, zero serialization; a crash takes the host with it, and it is **not** a `PreemptibleRuntime`, so `max_exec_timeout` is refused rather than approximated. **Output is routed, not seized.** A `_RoutedStream` is installed over `sys.stdout` and `sys.stderr` — each judged on its own, since using one as the sentinel for both either leaves a re-replaced stream unrouted or nests proxies until a write overflows the stack — and left there; it is a pass-through except for the context of a running cell, whose text and `.buffer` writes go to that execution's buffer (`_EXECUTION_OUTPUT`, a `ContextVar`). Swapping in a buffer for the duration of a cell claimed the whole process's output — a host thread logging while generated code ran had its line captured into the model's execution result and removed from where it was meant to go. Routing per context also means separate runtimes no longer interfere, so they need not be serialized against each other. stdout and stderr share one buffer, so `stderr` is preserved *and* keeps its place in the sequence. An asyncio task inherits the route, but the route is marked inactive when its cell ends so a later write falls back to the host instead of disappearing into an abandoned buffer. **Known boundary**: a thread the generated code starts does not inherit the execution context, so its output goes to the host stream rather than the result. Capturing it would mean wrapping every `Thread` target in the process — imposing new `threading` semantics on the host to serve this library, which is the trade this router exists to refuse. `IPyKernelRuntime` runs in a dedicated process, where standalone thread starts inherit the current cell's IOPub parent, each `ThreadPoolExecutor` submission captures the submitting cell, and each done callback captures the cell that registered it. Joined output reaches that cell, while a standalone thread that outlives it cannot be re-parented into a later result. Only messages owned by the current request refresh its silence timeout.

**Injections are queued, not written.** `inject_into_namespace` is synchronous and public, so it can land at any moment; the namespace is only consistent inside the gate. A whole batch is validated first (and serialized first by the kernel backend), then queued under the pending lock while the registry commit callback runs under that same lock. An execution can therefore observe either the whole registration or none of it, and an unsupported kernel value fails at registration rather than poisoning the next unrelated cell. Queued values are flushed before execution, reads and allocation, and *after* `reset` restores its snapshot, so a resource registered while a reset was queueing survives it rather than being wiped by it.

**One gate per executor** (`_Gate`) covers execute, `bind_unique` and `reset`, because a single `InteractiveShell` is not reentrant and all three mutate its namespace. It is cross-thread (a runtime may be driven from more than one loop, and an `asyncio.Lock` only excludes coroutines sharing its loop) and **fair** — served in arrival order, because an unfair gate let a steady stream of executions starve teardown indefinitely. Waiters poll rather than hand a blocking acquire to a worker thread: an acquire already dispatched cannot be cancelled, so a cancelled caller could take the gate and never release it. `bind_unique` records its persistent BaseRuntime binding before releasing that gate, and `reset()` obtains its binding snapshot only after entering it; otherwise reset can snapshot the registry between the backend bind and its registration, then erase the object behind a marker that was already returned. `reset()` clears *and restores* under the gate — re-injecting afterwards left a window where the namespace was genuinely empty. This backend also NFKC-normalizes names, since it resolves them with a dict lookup where generated code goes through the interpreter, which normalizes first.

**Cancellation is re-raised, not returned.** IPython catches `CancelledError` and hands it back as an ordinary cell result; passed on as one, a cancelled agent made another model call and reported `COMPLETED`. Each runtime builds an **independent** `InteractiveShell` (not the `.instance()` singleton) so runtimes in one process stay isolated.
- **IPyKernelRuntime** — separate Jupyter kernel subprocess, objects serialized via `dill`. Crash-isolated, and its `interrupt()` really works, which is what makes `max_exec_timeout` enforceable. `iopub_timeout` (default 30s) bounds *silence* between kernel messages, not total runtime — a cell printing periodically can run indefinitely, a silent one is cut off. Raise it for long silent computations.

  **Lifecycle transitions are atomic across the channel.** `_lifecycle_lock` serializes `start`/`stop`/`reset`, and a transition holds `_channel_lock` for its *whole* duration — `reset` does not release it between tearing the old kernel down and bringing the new one up, so a request queued behind it resumes against a live kernel instead of the `None` client that briefly sits in between (previously an `AttributeError` on every queued call, and two concurrent `reset()`s killed the kernel). Acquisition order is always lifecycle-then-channel and a request never reaches back for the lifecycle lock while holding the channel, so they cannot deadlock. Once process termination starts it finishes despite repeated caller cancellation; only then is the cancellation re-raised, so `stop`, `reset`, and failed startup cannot strand a live child after discarding its client. `_stop_locked` leaves a **fresh** `AsyncKernelManager` behind: a shut-down one cannot be restarted (its ZMQ context is closed, and `start_kernel` on it *hangs* rather than failing), so putting the rebuild in teardown is what makes `start()` work from any stopped state — and collapses `reset()` to stop-then-start.

  **Admission is one step.** `_admitted()` ensures the kernel is up *and* holds the channel, re-checking under the lock and retrying if a transition slipped in between. `start()` has a lock-free fast path, so "start, then take the channel" let a request queue behind a `stop()` already in progress and wake up holding the channel with a `None` client. **Teardown releases the channel and the process independently**, and replaces the manager only once the process is confirmed dead — one `try` around both meant a `stop_channels()` failure skipped the shutdown and still returned success, stranding a live subprocess with no handle left. **`_flush_injections` swaps its batch out before the first await**: `inject_*` is synchronous and public, so a registration made mid-flush mutated the dict being iterated and killed the execution carrying it. Cancellation waits for the dispatched injection before propagating. A failed dispatched injection is never re-queued — dill reconstruction is arbitrary Python and may already have produced a side effect — and the runtime refuses further requests until that binding is replaced or an explicit reset rebuilds the batch. Only successfully landed values enter the automatic restore set. Pending injections are protected by a thread lock, and when reset's binding snapshot is merged back, registrations made while reset was in flight win as the newer intent.

  **One loop at a time.** A kernel client's channels, futures and locks belong to the loop that created them, and `jupyter_client`'s do too, so overlapping loops simply hung — surfacing later as "lock is bound to a different event loop". `_single_loop` refuses an *overlapping* loop with a sentence instead, and covers lifecycle mutation (`reset`) as well as ordinary requests; otherwise a reset from loop B can tear the kernel out from under an execution on loop A. Only overlap: driving one runtime from a succession of loops (a module-scoped fixture with a loop per test, repeated `asyncio.run`) is ordinary and safe.

  **A kernel that survives its own shutdown is a distinct state.** Teardown asks up to `_SHUTDOWN_ATTEMPTS` (3) times — a single transport hiccup is common and recoverable — and `stop()` **raises** `RuntimeExecutionError` if the process outlives all of them, because returning success let a caller walk away from a running subprocess. `_orphaned` blocks `_start_locked` while it is still alive, keeping the manager that is the only handle to it. `_started` alone went false on a *failed* teardown too, so the next start called `start_kernel()` on that manager: Jupyter spawned a replacement that died on the occupied ports, execution silently reconnected to the old kernel, and the original handle was lost — while a log line claimed no new kernel would start. A retried `stop()` clears it.

  **Startup failure cleans up through `_stop_locked`, not `stop()`.** The public entry point takes `_lifecycle_lock`, which `_start_locked`'s caller already holds, and `asyncio.Lock` is not reentrant — so the cleanup deadlocked, the original failure was never raised, and a kernel that had already come up stayed alive with no handle left to reach it. That cleanup is shielded through repeated cancellation before the startup error or cancellation propagates. `_execute_silent` classifies both shell and IOPub timeouts as `RuntimeExecutionError` before cleanup runs; letting a bare `asyncio.TimeoutError` escape from public `start()` bypassed the runtime failure taxonomy.

  **Every request consumes both of its channels.** User execution consumes IOPub through `_collect_result` and then reaps its shell reply. Internal requests use `_request_reply`, which waits for IOPub `idle` before reading the shell reply — a long-running request is not expected to answer on shell while it is still busy. Draining only one side left the other queued without bound — after 1,200 executions the oldest unread reply was still execution 1, and every `_shell_reply_for` had that backlog to walk before reaching its own. Abandoned requests consume both sides inside `_abandon`; no caller reaps the same reply twice. `_request_reply` records `_recovering` **before** re-raising a caller's cancellation: an unreclaimed kernel is still running the wedged cell either way, and raising first dropped the flag on that path, so `_admitted()` handed the channel to the next request — precisely what `_abandon` exists to prevent.

  **Only `ok` is success.** `_execute_silent` allow-lists it rather than rejecting `error`, because ipykernel also answers `aborted` for a shell request queued when an interrupt aborts the batch — reachable, since `interrupt()` is public and lock-free. Treated as success, a flushed injection that never ran was recorded as landed and the model got a bare `NameError` for a name `describe_functions()` still advertised, while an aborted `_KERNEL_SETUP` left the executor started with no codec. It raises `RuntimeExecutionError`, not a bare `RuntimeError`: this escapes through `start()`, which the base envelope does not wrap.

  **`_collect_result` accumulates into a caller-owned list.** `_iopub_for` raises its silence timeout from inside the loop, so a frame-local list died with the frame and a cell that printed four hundred progress lines before stalling — including a traceback published just before it — handed the model nothing but the timeout message.

  **A timed-out or cancelled request reclaims the kernel.** `_abandon(msg_id)` interrupts, then gives that request a short `_INTERRUPT_GRACE_TIMEOUT` to reach `idle`. If it does not, the caller releases the channel and uses the ordinary serialized `stop()` lifecycle to terminate the process. Releasing a channel while its request still runs is never an accepted fallback — that let the next request interleave with the abandoned one and one slow request poisoned every request after it. Cancellation of `get_from_namespace` and `bind_unique` waits for their already-dispatched request to finish, commits any completed binding bookkeeping, and only then propagates; `execute` may interrupt because cancellation explicitly abandons user code.

  **The subprocess starts on demand**, inside `IPyKernelExecutor.start`: construction, registration and prompt rendering are all free, and the kernel appears on the first `execute()`/`get_from_namespace()`. A pure-chat run spawns nothing. `start()` is idempotent so paying the ~1s up front still works, and teardown stays explicit (`async with` / `stop()`). This deliberately replaced a `LazyRuntime` decorator: the deferral was already native to the class — only auto-start was missing — so a 230-line wrapper that duplicated the registry and widened the Protocol was not earning its keep. Requests are serialized on `_channel_lock`, because a kernel runs one cell at a time over a single shared IOPub queue. `stop()` waits on that lock so teardown doesn't yank the channels out from under a running request — graceful by default, matching `Executor.shutdown` / `shutdown_kernel(now=False)`. The wait is bounded by `_STOP_GRACE_TIMEOUT`, and an *immediate* shutdown composes from the existing primitive: `interrupt()` then `stop()`. Do not add a second shutdown mode for that.

**`reset()` semantics are identical across backends**: the namespace is cleared and every registered resource re-injected. The registry survives — a reset runtime is still the runtime the system prompt describes. On an unstarted kernel it short-circuits rather than spawning one to clear an already-empty namespace; the observable result is the same. (These two diverged previously: `IPythonRuntime` wiped its registry while `IPyKernelRuntime` re-injected, with tests asserting the opposite behaviours.)

**Names are claimed once, by every route that binds one.** `_claim_name` normalizes, validates, and reserves against functions, variables, types *and* raw bindings together — they all end up in one Python namespace, so per-registry checks let two entries bind the same variable while the prompt advertised both. An asynchronous `bind_unique` places its selected candidate in the same claimed-name set before touching the backend, then commits or rolls it back; this prevents a synchronous registration from claiming the candidate between lookup and binding without holding a thread lock across an `await`. Auto-injected types and raw injections go through the same checks: each used to overwrite an explicit registration silently. Auto-injection *declines* a taken name rather than raising, since the caller never asked for this type. Validation is `usable_identifier` — `isidentifier()` plus a *hard* keyword check, because `Variable("for")` passes the former and is a `SyntaxError` at the first execution that touches it. Soft keywords (`match`, `case`, `type`, `_`) are ordinary names in an assignment position and are accepted. Lookups (`retrieve`, `update_variable`) normalize but do not claim — they are asking about a binding, not making one. `bind_unique` validates the name it will *synthesize*, not the prefix, which is not what gets bound.

**Registrations are owned and batches are preflighted.** `BaseRuntime` shallow-copies `Function` / `Variable` / `Type` descriptors before storing them, so updating one runtime cannot change what another runtime restores on `reset()`. A per-runtime `RLock` covers the name snapshot, validation, backend staging and registry commit, so two threads cannot both successfully claim one name. `inject_resources()` validates every explicit and hidden name before committing any; skill exports, `_skill_store`, and `activate_skill` use that one batch so a late collision or serialization failure cannot leave earlier exports resident after agent construction fails.

Stopping a kernel queues the registry for the next one: the kernel takes the namespace with it while the registry outlives it, so a `stop(); start()` otherwise left the runtime advertising names the new kernel had never heard of. The executor retains the last successfully landed serialization of every persistent binding, including names allocated by `bind_unique`; shutdown therefore cannot be blocked by a mutable host object becoming unserializable after registration. Values still pending are carried separately and win over older landed values. Queued on stop rather than start, so starting an already-live runtime does not overwrite what the model has since done. `reset()` may build a newer snapshot while the old process is still usable, but once teardown succeeds it queues that snapshot *before* awaiting the replacement start, so cancellation or startup failure cannot split the registry from the next kernel namespace.

**Type auto-injection**: injecting a `Function` resolves postponed annotations with `get_type_hints` and walks its signature (recursing through generics, and considering each generic's **origin** as a candidate too — walking only the arguments left a user's `Cache[str]` with `Cache` uninjected while the prompt still advertised it); if the all-at-once resolution fails, each annotation is resolved independently so one missing forward reference does not hide valid custom types elsewhere. Injecting a `Variable` inspects its value's class. Custom types found are auto-injected with schemas *hidden*, so they are usable in generated code but invisible in `describe_types()`. Only an explicit `Type(cls, include_schema=True)` surfaces a schema. Explicit types are injected first so they win the name race; re-injecting a name raises `ValueError`.

**Typing machinery is not a user's class**, and enumerating it is hopeless: since 3.11 `typing.Any` *is* a class, so `f(x: Any)` registered a type named `Any` which then rejected the caller's own `Variable("Any", …)` — names are claimed across all registries — and `get_origin(int | None)` is `types.UnionType`, a class as well. `_TYPING_MODULES` matches those by module. `builtins` deliberately **cannot** join it: a class defined by `exec`-ing source into a bare namespace reports `__module__ == "builtins"` and is a genuine user type, which is what the value-based `_BUILTIN_TYPES` is still for. `TypeSchemaExtractor` recognizes both union spellings for the same reason — rendering `int | None` as `UnionType[int, None]` showed the model an expression it cannot write back, beside an `Optional[...]` that was fine.

**Kernel readiness**: `IPyKernelExecutor.start` delegates to `jupyter_client`'s `wait_for_ready` rather than hand-rolling a readiness loop. A `kernel_info_reply` on the shell channel is *not* sufficient evidence the kernel is usable: IOPub is ZMQ PUB/SUB, and a PUB socket silently discards anything published before the subscriber's subscription has propagated. The old loop broke on the shell reply alone and returned while IOPub was still dark, so the first cell's output was dropped and the call blocked until `iopub_timeout` with no error — an intermittent failure (~3 of 8 full-suite runs) that never reproduced in isolation. `wait_for_ready` loops until a shell reply *and* an IOPub message have both arrived, then flushes the channel. Do not replace it with a shell-only check.

**Resource hygiene**: both backends disable the history subsystem and the output cache — the kernel through `_KERNEL_ARGUMENTS` at `start_kernel`, the in-process shell through `create_ipython_config`. The kernel had no equivalent for a long time, so every cell ending in an expression pinned its value in `Out[n]` / `_` / `__`: `del df` freed nothing and an isolated kernel's memory only grew. What remains is IPython's single most recent execution result, which the next cell displaces — bounded, and the accumulation is what mattered. `create_ipython_config` sets `HistoryAccessor.enabled = False`. `history_length = 0` only bounds retention — the HistoryManager is still built, and each spawns an `IPythonHistorySavingThread` holding a SQLite connection, one per shell, never reaped. That leaked a thread and two fds per runtime, so a long-lived process building many runtimes accumulated both without bound. `TestResourceHygiene` guards it. (This was initially suspected of causing the intermittent kernel failures; it was not — see **Kernel readiness** above for the actual cause.)

### Model Abstraction (`models/`)

`Model` ABC (`base.py`) with `call()` and `stream()`. **`call()` is concrete** — a template method wrapping `_complete()`, which is the abstract method providers implement. That pulls response parsing inside the typed retry boundary, so a malformed body raises a classified `ModelError` rather than a bare `AttributeError`, and it mirrors the shape `StreamResponse` already had. Each provider previously wrapped itself in `with_retry_typed`, three near-identical copies that could drift. `stream()` returns a `StreamResponse` yielding `StreamDelta` objects where answer text (`content`) and reasoning (`thinking`) travel in **separate fields**, so reasoning never reaches the code parser. Terminal signals (`usage`, `finish_reason`) are attributes read after iteration, not deltas. Provider subclasses implement only `_open_stream()`.

**Chunk parsing is inside the error boundary.** `_process_stream_chunk` runs under `__anext__`'s classification, so a message shape this parser did not expect becomes a `ProviderError` rather than an `AttributeError` reported as `INTERNAL_ERROR` — a provider's message variants are as much a provider concern as its transport. A chunk carrying no `delta` is metadata, not content: Azure's asynchronous filter sends annotations that way.

`Model.filters_asynchronously` declares that a provider may send its filter verdict *after* the content it applies to. `OpenAIModel` and `LiteLLMModel` expose it as an explicit constructor option (not a wire parameter). The agent normally stops at the first complete code block and runs it; against such a provider it reads to the end of the stream first, because otherwise it executes code the verdict is about to withdraw. Off by default — the wait costs a whole generation, and providers that filter before streaming never need it. Content *plus* a `content_filter` finish is not an answer and is not recoverable: the fragment is neither persisted into history nor sent back for continuation. Natural EOF without a terminal finish reason is never completion: ordinary content enters output recovery, while asynchronously filtered content fails closed because transport completion is not filter approval. A closed code block followed by `length` is executable — the cap describes only trailing text the ordinary early-stop path deliberately ignores.

**Terminal fields are independent.** Usage, finish reason and a final delta may share one provider event (Anthropic's terminal `message_delta` carries usage and stop reason together), so parsing one must not return before the others are inspected. OpenAI's usage-only terminal chunk is merely the sparse case, not the universal shape.

`StreamResponse` accumulates `thinking` and `refusal` alongside the content stream — both are prose, and neither should reach the code parser. A refusal is an answer; reasoning alone is not. Any terminal response with no content, refusal or closed code block becomes a typed model failure rather than an empty `COMPLETED`.

`ModelResponse.usage` carries token counts under the same field name every other carrier uses (`StreamResponse.usage`, `StoppedEvent.usage`, `AgentResponse.usage`). When a stream reports zero usage, the agent estimates the request unconditionally from the wire plus content/refusal/reasoning, including when the transport fails before any answer content arrives; conditioning that fallback on a successful loop exit made billed reasoning-only failures free, silently bypassing budgets.

`Model.max_output_tokens` is a declaration the compactor uses to size its threshold. `LiteLLMModel` also sends it (as `max_tokens`), so its declaration cannot drift from the request. `OpenAIModel` deliberately does **not**: o-series models reject `max_tokens` and want `max_completion_tokens`, so which key to send is the caller's call — pass it through kwargs. Sizing a compaction threshold and capping generation are separate concerns, and only the second depends on the model family.

**Resilience layer** — the invariants here are load-bearing:
- `retry.py` — exponential backoff + jitter capped at 32s, honoring `Retry-After`. A definite HTTP status is authoritative (a 400 mentioning "timeout" is *not* retried); billing exhaustion is never retried despite riding a 429. The message-text tier is a last resort for SDK errors and never applies to Python's own programming errors — a `TypeError` for a kwarg that happens to be named `request_timeout` is deterministic, and retrying it spent the whole backoff budget before surfacing an immediate failure.
- `errors.py` — `classify_provider_error()` is **total**: it returns a `ModelError` for every input, falling back to `ProviderError`. Totality is the point — with a partial function every call site needs its own fallback, and every fallback is a leak. `raise_model_error()` is the single raise-with-`__cause__` helper; the typed classes (`PromptTooLongError`, `ProviderBillingError`) are what route overflow to compaction instead of crashing. HTTP 413 is a structured prompt-overflow signal alongside OpenAI's `context_length_exceeded` code.
- `StreamResponse.__anext__` retries a transport failure **only before semantic output is received** (`_received_output`); later would replay content. Refusal counts even though it bypasses the code parser and is not yielded as a `StreamDelta` — retrying after one duplicated the refusal. Once a terminal `finish_reason` has arrived, a subsequent read failure only loses optional trailing accounting and ends iteration — asking the model to resume an answer the provider already declared complete changes the answer.
- `StreamResponse.aclose` classifies failures for direct callers. The agent's
  per-turn `_close_stream` treats them as cleanup and logs them, so a reset
  while closing cannot invalidate a completed answer or replace the read
  failure being cleaned up. The connect-retry path likewise suppresses
  `ModelError` around the stream it is already discarding.
- `stream_with_idle_timeout()` is a sliding watchdog on *item* progress, not socket bytes — proxy keep-alives and provider pings keep a socket readable while producing nothing. It does **not** count a `StreamResponse`'s own connect-retry backoff, which sleeps *inside* the `__anext__` it wraps: the stream announces the wait through `on_backoff` and the window is rescheduled past it. Counting it meant a server's `Retry-After: 30` spent a quarter of the default 120s window per attempt, and the run ended as a stall with retries still unspent — the watchdog policing the client's own patience. `LiteLLMModel` assigns `max_tokens` rather than `setdefault`-ing it for a related reason: an explicit `max_tokens=None` is a *present* key, so setdefault kept the None and silently dropped the declaration the compactor sizes against.

Runtime failures get the same treatment on their own side: `runtime/base.py::_containing_backend_failures` is the single envelope converting anything an executor raises into `RuntimeExecutionError`, shared by `execute` and `bind_unique`. When only `execute` had it, an allocation that timed out escaped untyped and ended the run as `INTERNAL_ERROR` for a runtime that was merely slow. `IPyKernelExecutor` deliberately does **not** wrap transport faults in an `ExecutionResult` — that would hand the model "your code failed" for a dead kernel.

Providers are imported eagerly in `models/__init__.py`, but their SDKs (`import openai`, `import litellm`) are imported inside method bodies, so the classes are always importable and only *instantiating* one needs the extra.

### Messages (`messages.py`)

Five roles, two of them internal: `CODE_EXECUTION` and `EXECUTION_RESULT` describe the code/result rhythm. `Message.wire_role` maps them to `assistant` / `user`, and `to_wire()` renders the list for a provider. Compaction selects on these subclasses (microcompaction targets `ExecutionResultMessage`), so code that rebuilds history must preserve them rather than flattening to `UserMessage` / `AssistantMessage`.

`agent._prepare_messages()` inserts a `<system-reminder>` user message carrying the current time right after the system prompt, keeping the system prompt byte-stable across turns for prompt caching. `build_system_prompt` still passes `current_time` to the template — `str.format` ignores unused kwargs, so the default template stays byte-stable while a caller's template copied from ≤0.8 (which carried `{current_time}`) renders instead of raising `KeyError` on every run.

An execution failure with no stdout is rendered as its error (`MemoryError: …`), never as the empty-output placeholder: the executor's catch-all can return an error-only result when the execution machinery itself raised, and "No output" read as success — the model answered from state the code never created. Output recovery records the partial assistant turn **only when it has text**: a reasoning model can spend the whole completion cap on thinking (`finish_reason="length"`, zero visible content), and an empty assistant message poisoned history against providers that reject empty content with a definite 400, which is never retried.

### Context Compaction (`compaction/`)

All compaction flows through `Compactor` (`compaction/compactor.py`), which owns the summarization model, the budget config and the circuit-breaker state. `CaveAgent` builds a default one; pass `compactor=Compactor(model=cheap_summarizer, context_window=200_000, token_estimator=tiktoken_len)` to override.

`threshold()` precedence: explicit `output_reserve` → the **adopted** generating-model declaration (`adopt_output_reserve`) → the compactor's own model declaration → a conservative fallback. Tested against `None`, not falsiness, so an explicit reserve of `0` is honoured. The reserve holds room for the *agent's* next completion, but a `Compactor` resolves it from its own model — which in the documented `Compactor(model=cheap_summarizer, …)` setup is the summarizer, whose 1024 against an agent generating 8192 left the threshold ~7k too high and returned a prompt that still overran the window. `CaveAgent.__init__` therefore *adopts* its model's declaration into the compactor. Adoption is a separate field, never a write to `output_reserve`: overwriting it made the adopted value indistinguishable from a caller's explicit reserve and mutated configuration shared between agents. Multiple adopters keep the largest declaration — over-reserving compacts a little early, under-reserving overruns the window.

`_summary_request_too_large` is bounded by that same `threshold()`, not by an inline `context_window - reserve`. Splitting cannot shrink a request's *fixed* part, so an unfloored limit (a reserve at or above the window) made every request too large and `_fold_summary` bisected to single characters, issuing a real model call at each of thousands of leaves.

**A summary is committed only if the provider says it finished.** `_reject_unusable_summary` accepts only `finish_reason == "stop"` and rejects a refusal before the text is used. An allow-list is required here: a missing or future finish reason is not affirmative evidence that a lossy operation completed. Judging by text cannot work — a refusal reads like prose and a truncated summary reads like a summary — so "is it non-empty" committed both, replaced the history they were meant to distil, and recorded a *success* against the circuit breaker. `ModelResponse.refusal` is carried separately from `content` for this: as an answer a refusal is what the user should see, as a product it is a failure, and only the caller knows which it needs.

Three tiers:
1. **`microcompact()`** — no LLM. Clears older execution results, keeps the most recent 6, returns `(messages, needs_summarize)`, and runs silently.
2. **`summarize()`** — LLM-summarizes the older half; the tier the agent announces via `StatusType.COMPACTING`. Circuit-breaker protected: 3 consecutive failures trip it, and it counts down `COOLDOWN_ATTEMPTS` summarization attempts before letting the model be retried. The countdown is internal state with no caller-supplied argument — an earlier design took the step number from the caller, the one production call site never passed it, and the breaker latched open for the whole session.
3. **`recover_from_overflow()`** — emergency path once the API has rejected the prompt; keeps the most recent quarter, no breaker.

Summary requests are folded in capacity-bounded batches. A known oversized request is bisected before sending; a provider `PromptTooLongError` triggers the same adaptive split, down to part of one large message. Each successful batch updates the prior summary before the next batch, so every source fragment reaches a completed summarization request. If summarization still fails, both normal compaction and overflow recovery preserve the unsummarized history (overflow recovery may already have applied the documented microcompaction tier); provider unavailability is never permission to trim turns permanently.

**Re-compaction is incremental.** If the region already carries a summary, that summary is handed back to the model VERBATIM with every complete turn after it transcribed, and the model is asked to *update* rather than re-compress. The production summarization path disables `format_transcript`'s optional display cap: truncating a message before summarization permanently deletes its unseen suffix when the original history is replaced. Re-summarizing a summary loses fidelity every pass. When nothing followed the prior summary, the LLM call is skipped entirely.

**A summary is identified by its type, never its text — and so is its acknowledgement.** `SummaryMessage` (a `UserMessage` subclass carrying `body`) and `SummaryAcknowledgementMessage` are what compaction matches; the `<conversation-summary>` envelope in the content is *presentation*, so the model can tell a summary from an instruction. Three earlier attempts made text the evidence — a `[Previous conversation summary]` prefix, then the envelope, then the acknowledgement's wording — and each fell the same way: a summary is delivered into a conversation whose other participant also writes text, so any marking syntax can be reproduced in an ordinary request. Matching the ack's *text* additionally deleted genuine assistant turns that happened to say it. A type cannot be typed.

Histories written by ≤0.8.0 carry no type, so they are converted by `migrate_legacy_summaries()` — an explicit call the caller makes about a history whose origin it knows, never a guess made on every compaction. That invocation *is* the provenance the bytes cannot carry. An unmigrated legacy history is simply re-summarized: fidelity lost, nothing corrupted. The two error directions are not symmetric — a fabricated summary drops the real turns as "already covered" and carries the impostor's text forward in their place.

**Estimates are anchored, not maxed.** `TokenAnchor` pairs an API-reported prompt size with the heuristic reading taken at the same moment, and `estimate_tokens` returns `api_tokens + (heuristic_now - heuristic_then)`. It used to be `max(heuristic, api_count)`, which sounded like it covered messages appended after the measurement but did not: a real conversation's API count dwarfs the heuristic, so `max` returned it unchanged and every later turn — including a multi-thousand-token execution result — was invisible until the bare heuristic overtook it. A **shrunken** history invalidates its own anchor (`heuristic < baseline` → fall back to the heuristic), so compaction rewriting the message list needs no caller to remember to clear anything.

**Token estimation** (`compaction/tokens.py`) is expressed in **tokens per character** — `DEFAULT_TOKENS_PER_CHAR = 0.25`, `LIGHT_NON_LATIN_TOKENS_PER_CHAR = 1.25`, `DENSE_NON_LATIN_TOKENS_PER_CHAR = 1.75`, `RARE_SCRIPT_TOKENS_PER_CHAR = 3.5`, `CJK_TOKENS_PER_CHAR = 1.25`, `SUPPLEMENTARY_CJK_TOKENS_PER_CHAR = 4.0`. Rates are a table of character *classes* (`_RATED_CLASSES`), not a single CJK flag, which is what made room for the rest: no vocabulary in this class has space for supplementary-plane ideographs, so each costs 3–4 tokens and charging them the BMP rate under-counted threefold. Everything that was neither Latin nor CJK fell through to the Latin rate for the same reason — emoji charged 0.25 against a true 2.6, Thai and Devanagari 4× under. Three tiers rather than one, because the span runs from Cyrillic at 0.54 to Cherokee at 3.27 and a single rate covering the dense end would bill Russian six times over: over-estimating is the safe direction, not a free one. Class rates are measured per *script* character — a sample's whole token count over only its non-Latin characters — since averaging over the mixed sentence lets its ASCII dilute the rate ~2× and reintroduces the under-count. `_RATED_CLASSES` must stay **disjoint**: matches are counted per class and subtracted from the default-rate remainder, so an overlap charges twice. The predecessor stored the inverse (`chars // 4`), a form that cannot express a rate above 1 token/char at all, which CJK is; that was a unit bug, not a constant needing a tune. Rates take the *dense* end of their measured span because the directions are not symmetric: over-estimating compacts a little early, under-estimating lets the prompt cross the real limit and the API rejects it. There is no density threshold — the old 30% cutoff charged the Latin rate to *every* character of any text below it, so a Chinese question about an English stack trace was under-counted ~3×. The CJK regex is derived from the range table so there is no second copy, and the table includes CJK punctuation (fullwidth `，？！` measure ~1 token each). `tiktoken_estimator()` is the opt-in exact path for `Compactor(token_estimator=...)`. Known and deferred: Python and JSON measure 0.39–0.43 tok/char but are charged 0.25 — a role-aware rate is the fix; `test_latin_rate_still_under_counts_dense_structured_text` asserts the gap so it cannot drift unnoticed.

**The split never separates a code message from its result.** `_align_split_to_pairs` moves the boundary *backward* so both stay in the kept tail. The predecessor split anywhere and then deleted the orphaned result — which, sitting past the split, reached neither the summarizer nor the kept history: a computation's only output vanished while the code that produced it stayed behind describing it. Keeping more than asked is the safe direction; deleting the only copy is not.

`_tokens_after_microcompact` subtracts what microcompaction actually saved rather than re-estimating. Re-estimating swaps the API-anchored count for the bare heuristic, which routinely reads much lower, so the cheap tier would look sufficient whenever the heuristic under-counts and summarization would be deferred until the API rejected the prompt.

A `<persisted-output>` marker is not cleared to the generic placeholder during microcompaction — only its preview is stripped, keeping the declaration line that names the runtime variable still holding the full text.

**The keep-window is measured over every execution result, then narrowed to those still worth clearing.** Measuring it over only the *unfloored* ones made an already-floored result invisible to the window — and a persist marker built with `exec_output_preview_chars=0` is at its floor from birth — so a run whose recent results were all such markers kept the six *oldest*, largest results as if they were recent, and the cheap tier reclaimed nothing before escalating to summarization.

**Re-summarization drops every summary, not just the newest.** The newest subsumes its predecessors, so a straggler in a rehydrated history was transcribed into the new-turns block as a turn that happened *after* the summary — the conversation re-narrated as something following its own recap.

### Oversize Execution Output (`_placeholders.py`)

When stdout exceeds `max_exec_output`, the full text is bound to a runtime variable and the model receives a `<persisted-output>` marker naming it plus a leading preview. **The runtime allocates the name**, via `await Runtime.bind_unique(prefix, value, start=…)`, and each backend does it **in the namespace the generated code actually runs in**. A registry on the agent's side could not see a caller's registered `Variable("_output_1")`; a registry on the runtime's side still could not see one the *model* created in a code block. Both were overwritten with a string. The in-process backend reads `user_ns` between awaits; the kernel backend asks which names are taken and then injects, holding `_channel_lock` unbroken across both — nothing in this runtime reaches the kernel without that lock, so the pair is indivisible with respect to everything that could slip between them, including the model's own code. Before releasing that lock, each executor invokes BaseRuntime's registration callback; reset/stop take their restore snapshot only after acquiring the same gate, so a successful allocation cannot be erased by a stale snapshot. Asserted behaviourally — 25 concurrent allocations yield 25 distinct readable names — rather than by inspecting for `await`, since the kernel path must await.

**Generated helper code binds only its target.** Kernel setup stores dump/load callables under a dictionary key that is not a Python identifier; the callables capture `dill` and `base64` before generated code runs. User expressions reach that entry through a fresh function object's globals, so shadowing `display`, `get_ipython`, `globals`, `__import__`, or even replacing `__builtins__` cannot break reads and persistence. The setup's temporary names are deleted, and injection code adds only its requested target. An allocator that used scratch globals overwrote — and then `del`'d — any variable of the model's sharing those names, which is the defect the allocator exists to prevent, one level down.

`bind_unique` normalizes the prefix at the `BaseRuntime` boundary every backend shares, and the kernel backend again on the way in, because it compares names as strings and must compare the ones Python will bind. The agent's prefix is NFKC-normalized and then validated at construction (`f"{prefix}_1".isidentifier()`). Normalization is what Python does when it *binds* a name, so skipping it let `K` (U+212A KELVIN SIGN) pass validation while the code bound `K_1`: in-process the model got `NameError` following its own pointer, and on the kernel the allocator's "is this taken?" check never matched what it had bound and handed out `K_1` twice: it becomes a Python name the model is told to slice, and accepted blind it produced a marker naming `bad-name_1`, read as a subtraction in-process and a `SyntaxError` on the kernel. `highest_persisted_index` builds its pattern from `re.escape(prefix)` for the same reason — a fixed `[A-Za-z_]` class recognized only ASCII prefixes while validation accepts any identifier, so `输出`'s markers matched nothing and a resumed session re-pointed the first session's marker at the second session's output.

The agent still supplies a floor (`highest_persisted_index` over resumed history): names promised to a model in an earlier run live in the conversation, not in the namespace, and reusing one would re-point a marker the model still trusts. A marker in history is a pointer, so a shared name did not "keep the newest" — it re-pointed every earlier marker at text it never described. `build_persist_marker`'s `variable` parameter is required for the same reason, and `_shape_output` returns `(body, name)` so the event and the marker cannot name different variables. Because the runtime *is* Python, that variable is a first-class object the model can slice, search or re-parse — no file round-trip and no re-running code that may be slow, expensive, or not reproducible. (The previous behaviour discarded the output entirely and told the model to print less.)

Model-facing text lives in three modules by role: `_placeholders.py` holds the reactive sentinels and markers the agent splices into history, `prompts.py` the authored system prompt and per-turn wrappers, `compaction/prompts.py` the summarization prompts. `build_persist_marker` / `strip_persisted_preview` live together so the marker format can't desynchronize between producer and consumer.

### Security (`security/`)

AST-based `SecurityChecker` with `ImportRule`, `FunctionRule`, `AttributeRule`, `RegexRule`. Applied in the executor layer; violations short-circuit execution and surface as `SecurityErrorEvent`.

This is **advisory hardening, not a sandbox** — static analysis can't catch dynamic reflection or C-extension escapes. Untrusted code needs a real isolation boundary (container + seccomp/gVisor + OS limits) with `IPyKernelRuntime`. Rule specifics: `ImportRule` matches the top-level package (forbidding `os` also blocks `import os.path`); `FunctionRule` flags both calls and bare-name references (catching `f = open`) and matches attribute calls by method name, so forbidding `open` also blocks `path.open()`; `RegexRule` scans the unparsed source of the whole module.

### Skills System (`skills/`)

Implements the Agent Skills open standard. A skill is a directory with `SKILL.md` (YAML frontmatter + markdown) and optional `injection.py` exporting `Function` / `Variable` / `Type` objects via `__exports__`. Instructions are progressively disclosed by `activate_skill(name)`. Runtime resources are registered up front as one atomic batch of hidden raw bindings: they do not enter the prompt, collisions fail before any export is committed, and the runtime can restore them after `reset()`. Activation mutates no namespace state. Raw bindings get the same signature/type walk explicit registration performs — a skill's instructions tell the model to construct the custom types its function signatures name, and skipping the walk left `Order` in the instructions and a `NameError` in the namespace.

`injection.py` is executed at discovery time, before any security checker exists — skills are trusted code. It is **registered in `sys.modules` before execution and left there**: anything resolving a class back to its module looks it up there, so an unregistered module made every skill combining `from __future__ import annotations` with `@dataclass` die inside `dataclasses._is_type` on `'NoneType' object has no attribute '__dict__'` — an error naming nothing near the cause — and broke `get_type_hints()` on skill-defined classes, which type auto-injection calls. A module whose execution fails is removed again.
